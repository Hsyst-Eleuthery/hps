# Changelog — HPS
## Release v5 (v14) vs Release v4.5.2 (v13.1)

Thaís (op3ny)

---

## Visão geral

Este changelog documenta de forma detalhada e abrangente as diferenças entre a Release v4.5.2 (v13.1-release, codinome "HPS fix2") e a Release v5 (v14-release, codinome "Economy Update - HPS Mobile"). A Release v5 representa a evolução mais significativa, mais ambiciosa e mais completa do ecossistema HPS desde sua criação, com foco em três grandes eixos de desenvolvimento: segurança distribuída (o protocolo 2S+1U+1M com suas dez fases), extensão móvel (os novos aplicativos HPS-Mobile e HPS-Wallet para Android) e robustez da economia interna (supply cap, fee market, PHPS Titles, voucher supply chain e content receipt chain). Esta versão transforma o HPS de um ecossistema restrito a desktops com segurança básica em uma plataforma federada robusta, auditável e acessível de qualquer lugar.

## 1. Novos componentes

### 1.1 HPS-Mobile (NOVO)

O HPS-Mobile é um aplicativo completamente novo, desenvolvido do zero para a Release v5, que representa a primeira extensão do ecossistema HPS para dispositivos móveis. Implementado em .NET MAUI (Multi-platform App UI) para Android com target framework net10.0-android e API mínima 21 (Android 5.0 Lollipop), ele oferece um cliente funcional e completo que permite ao usuário interagir com todos os subsistemas principais do HPS diretamente de um smartphone ou tablet Android.

**Estrutura de arquivos (44 arquivos total):**
- 9 arquivos de serviços (comunicação Socket.IO, API HTTP, criptografia, PoW, armazenamento seguro, estado de sessão)
- 7 páginas de interface (Login, Browser, Carteira, Mineração, Rede, Ajuda, Ban)
- 1 popup de PoW para exibição de progresso
- Configuração Android (AndroidManifest.xml, security config, data extraction rules)
- AppShell.xaml para navegação por tab bar
- App.xaml.cs para inicialização

**Funcionalidades incluídas:**
- Autenticação por challenge-response com verificação mútua (cliente prova chave privada, servidor prova identidade)
- Navegação de conteúdo hps:// com resolução de domínios e inspeção de contratos
- Carteira HPS completa com envio, recebimento, histórico e cotações de exchange
- Mineração PoW com slider interativo de configuração de threads (1 a MaxPowThreads)
- Mineração contínua com agendamento automático (ativa mineração indefinidamente)
- Reconexão automática com backoff exponencial (1s → 2s → 4s → ... → 30s, máx. 10 tentativas)
- Keepalive com timeout de 120 segundos para detecção de conexões mortas
- Armazenamento seguro de credenciais via SecureStorage nativo do Android (KeyStore)
- Lista de servidores recentes (até 5 endereços memorizados)
- Toggle SSL/TLS para conexão segura ou não-criptografada
- Notificações de ban com contagem regressiva de duração
- Aceitação de contrato de uso na primeira conexão
- Navegação por tab bar com 5 abas: Navegar, Carteira, Mineração, Rede, Ajuda

**Tecnologias utilizadas:**
- .NET MAUI 10.0 (net10.0-android)
- CommunityToolkit.Maui (navegação e utilitários)
- CommunityToolkit.Mvvm (padrão MVVM com data binding)
- SocketIOClient (comunicação WebSocket em tempo real)
- RSA-4096 (chaves criptográficas)
- SecureStorage (armazenamento seguro Android)

### 1.2 HPS-Wallet (NOVO)

O HPS-Wallet é um aplicativo dedicado exclusivamente para operações financeiras, desenvolvido do zero para a Release v5. Implementado em .NET MAUI para Android, ele oferece uma interface simplificada e focada em usabilidade para usuários que precisam apenas de funcionalidades de carteira sem a complexidade do cliente completo HPS-Mobile.

**Estrutura de arquivos (17 arquivos total):**
- 7 arquivos de serviços (comunicação, API, criptografia, PoW, armazenamento, estado, eventos)
- 4 páginas (WalletMain, Login, Pending, PowPopup)
- Configuração Android e inicialização do app

**Funcionalidades incluídas:**
- Leitura de QR codes via ZXing.Net.Maui para entrada de endereços sem digitação manual
- Exibição de saldo com atualização automática em tempo real
- Envio de HPS para outros usuários com confirmação por assinatura
- Recebimento de HPS com exibição de endereço e QR code
- Histórico completo de transações com detalhes de cada operação
- Cotações de exchange obtidas diretamente do servidor
- Gerenciamento de transferências pendentes com aceite, rejeição ou renúncia
- Notificações de oferta de vouchers com confirmação automática por assinatura
- Eventos de atualização economia (notificações de mudanças no mercado)
- Notificações de retenção de vouchers (informando indisponibilidade temporária)
- Fluxo de autenticação com challenge-response

**Diferencial em relação ao HPS-Mobile:**
O Wallet é mais leve, mais rápido e mais focado. Enquanto o Mobile oferece todas as funcionalidades do ecossistema (navegação, mineração, rede, carteira), o Wallet concentra apenas em operações financeiras, tornando-o ideal para uso cotidiano de pagamentos e recebimentos sem a sobrecarga de funcionalidades que o usuário pode não precisar.

## 2. Protocolo 2S+1U+1M (NOVO)

O protocolo 2S+1U+1M é a adição mais significativa, mais ambiciosa e mais transformadora da Release v5. Ele define o requisito mínimo de rede para operação completa do HPS — 2 Servidores + 1 Usuário + 1 Minerador — e implementa dez fases de segurança distribuída que, juntas, criam uma camada robusta e verificável de proteção contra fraude, censura, manipulação e falhas. Todas as 10 fases foram concluídas e implementadas na Release v5, representando uma transformação completa da postura de segurança do sistema.

### Fase 1: Handshake efêmero entre servidores

**O que é:** Um protocolo de autenticação temporária e mutuamente verificável entre servidores da federação.

**Como funciona:** Quando dois servidores precisam se comunicar — para validar uma exchange, confirmar um voucher, sincronizar dados ou realizar qualquer operação inter-servidor —, eles realizam um processo formal de autenticação que inclui: geração de nonce aleatório pelo servidor iniciador (número de uso único), assinatura do nonce com a chave privada RSA-PSS do servidor, envio do nonce assinado ao servidor receptor via endpoint POST /handshake/init, verificação da assinatura pelo receptor usando a chave pública do iniciador, geração de nonce pelo receptor, assinatura e envio de volta via POST /handshake/complete, e verificação final pelo iniciador.

**Por que é importante:** Todo o processo tem TTL (Time To Live) de 5 minutos, expirando automaticamente e exigindo renovação contínua. Isso garante que a confiança entre servidores nunca se torna estática ou permanente, forçando verificação periódica e impedindo que credenciais comprometidas permaneçam válidas indefinidamente.

**Novos endpoints:**
- POST /handshake/init — Inicia o handshake com envio de nonce e assinatura
- POST /handshake/complete — Finaliza com verificação cruzada e establishment da sessão

**Nova tabela SQLite:** server_handshakes — Armazena registros de handshakes com TTL, nonces e estado

### Fase 2: Confirmação cruzada de vouchers

**O que é:** Mecanismo que requer confirmação de pelo menos 1 outro servidor antes de considerar um voucher válido para operações significativas.

**Como funciona:** Quando um voucher é submetido a uma operação de exchange, transferência ou validação, o servidor que recebe a operação pode solicitar confirmação de um ou mais servidores adicionais da federação. Essa confirmação é registrada em tabela dedicada com timestamp preciso, hash do voucher confirmado e identidade do servidor confirmador.

**Por que é importante:** Previne fraudes em que vouchers forjados ou duplicados seriam aceitos por um único servidor. A verificação entre servidores cria uma rede de confiança mútua que não depende de autoridade central.

**Novos endpoints:**
- POST /voucher/confirm — Solicita e registra confirmação cruzada de voucher
- GET /voucher/{id}/receipt — Retorna comprovação de confirmação

**Nova tabela SQLite:** voucher_confirmations — Registros de confirmação com timestamp, hash e servidor

### Fase 3: Travas anti-double-spend

**O que é:** Mecanismo que previne o gasto duplo de vouchers durante operações de exchange — um dos riscos mais sérios em qualquer sistema de valor digital distribuído.

**Como funciona:** Quando um voucher entra em processo de exchange, ele é imediatamente travado por 60 segundos, impedindo que seja usado simultaneamente em outra operação em qualquer servidor da rede. A trava pode ser confirmada entre servidores via POST /voucher/lock/confirm, garantindo que o estado de trava é consistente na federação. Se a trava expirar sem confirmação, o voucher é automaticamente liberado.

**Por que é importante:** Em um sistema distribuído, o mesmo voucher poderia teoricamente ser enviado simultaneamente para dois servidores diferentes (ataque double-spend). As travas eliminam essa possibilidade temporalmente, dando tempo para confirmação entre servidores antes que o valor seja gasto definitivamente.

**Novos endpoints:**
- POST /voucher/lock — Inicia trava anti-double-spend em um voucher
- POST /voucher/lock/confirm — Confirma trava entre servidores
- POST /voucher/spent — Notifica que voucher foi gasto definitivamente
- GET /voucher/{id}/lock-status — Consulta estado atual da trava

**Nova tabela SQLite:** voucher_locks — Registros de trava com TTL, estado e confirmações

### Fase 4: Assinatura dupla de conteúdo

**O que é:** Mecanismo de proteção contra censura que registra conteúdo em dois servidores distintos, ambos assinando independentemente o registro.

**Como funciona:** Quando um conteúdo é publicado com proteção de assinatura dupla, ele é registrado em dois servidores diferentes da federação. Cada servidor gera um contrato de registro assinado com sua chave privada, e ambas as assinaturas são armazenadas e vinculadas ao conteúdo. Se um servidor for comprometido ou forçado a remover o conteúdo, o outro mantém o registro original com ambas as assinaturas, preservando a integridade histórica.

**Por que é importante:** Em um sistema distribuído, a resistência à censura não pode depender da boa vontade de um único operador. A assinatura dupla constrói resistência à censura na própria arquitetura do protocolo.

**Novos endpoints:**
- POST /content/register — Registra conteúdo com assinatura dupla em dois servidores
- POST /content/replicate — Solicita replicação de conteúdo entre servidores
- GET /content/{hash}/registration — Retorna informações de registro e assinaturas

**Nova tabela SQLite:** content_dual_registrations — Registros de assinatura dupla com ambas as assinaturas

### Fase 5: Validação cruzada de transferências

**O que é:** Mecanismo que requer validação de 2 servidores antes de processar transferências de valor significativas.

**Como funciona:** Antes de uma transferência de valor entre usuários — especialmente transferências que atravessam servidores diferentes — ser finalizada, ela precisa ser validada por pelo menos dois servidores independentes da federação. Cada servidor verifica a legitimidade da transferência, a disponibilidade dos vouchers, a coerência com o estado da rede e a ausência de conflitos com outras operações pendentes.

**Por que é importante:** Previne que um único servidor comprometido, malicioso ou com erro de validação possa processar transferências fraudulentas, duplicadas ou inconsistentes.

**Novos endpoints:**
- POST /transfer/validate — Solicita validação cruzada de transferência
- POST /transfer/notify — Notifica que transferência foi processada com sucesso

### Fase 6: Monitoramento de estabilidade de nós

**O que é:** Sistema que avalia continuamente a saúde dos servidores da federação e classifica它们 em três níveis de estabilidade.

**Como funciona:** O sistema monitora continuamente métricas de cada servidor — tempo de resposta, taxa de sucesso em operações, consistência de dados entre sincronizações — e classifica cada nó como: Estável (funcionamento normal, todas as métricas OK), Degradado (problemas menores ou temporários) ou Instável (problemas significativos e persistentes). Nós instáveis têm operações econômicas bloqueadas automaticamente.

**Por que é importante:** Previne que problemas localizados em um servidor se propaguem e afetem a economia de toda a rede. É uma forma de "quarentena" automática e baseada em métricas.

**Novo endpoint:** GET /node/status — Retorna status de estabilidade do nó

**Novos arquivos Go:** node_stability.go — Lógica de monitoramento e classificação

### Fase 7: Contratos de auditoria

**O que é:** Mecanismo que gera automaticamente contratos assinados com estatísticas do servidor a cada login ou cadastro de usuário.

**Como funciona:** A cada vez que um usuário faz login ou se cadastra no servidor, o sistema gera automaticamente um contrato de auditoria assinado criptografamente que contém: número total de usuários, quantidade de vouchers em circulação, volume de conteúdo armazenado, estado da rede, taxa de erros e outros indicadores de saúde. Esses contratos são armazenados em cadeia com encadeamento hash.

**Por que é importante:** Cria um registro imutável, verificável e auditável do estado do servidor ao longo do tempo, permitindo que qualquer participante verifique se o servidor está operando consistentemente e se suas estatísticas são coerentes.

**Novo endpoint:** POST /server/audit — Gera contrato de auditoria sob demanda

### Fase 8: Verificação de integridade do código

**O que é:** Mecanismo que garante, de forma verificável, que o servidor está executando o binário compilado a partir do código-fonte esperado.

**Como funciona:** Um script de compilação (generate_code_hash.go) calcula o hash SHA-256 de todos os 73 arquivos fonte (.go e .sql) e embute o resultado como constante no binário do servidor (arquivo codegen.go). Qualquer cliente pode solicitar o hash via GET /server/integrity e compará-lo com o hash esperado.

**Por que é importante:** Detecta adulterações no código-fonte — seja modificação maliciosa, correção não documentada ou qualquer alteração não autorizada. É uma forma de garantir que o que o servidor diz ser é realmente o que está executando.

**Novo arquivo Go:** codegen.go — Hash compilado do código-fonte (gerado por script)

### Fase 9: Desafios de comportamento (challenge-response)

**O que é:** Mecanismos ativos e periódicos que verificam se um nó está se comportando corretamente de acordo com as regras do protocolo.

**Como funciona:** O sistema envia desafios categorizados em quatro tipos: crypto (verificação de operações criptográficas), consistency (verificação de consistência de dados), protocol (verificação de aderência ao protocolo) e computation (verificação de trabalho computacional real). Um servidor pode ser desafiado a qualquer momento e precisa responder corretamente dentro de um prazo.

**Por que é importante:** Verifica continuamente que os servidores estão operando honestamente, não apenas no momento da autenticação, mas ao longo de toda a operação. Falhas em responder resultam em penalidades.

**Novos endpoints:**
- POST /server/challenge — Envia desafio de comportamento
- GET /server/verify — Verificação completa de comportamento

### Fase 10: Sistema completo de auditoria

**O que é:** Sistema abrangente de auditoria que inclui score de saúde, detecção de anomalias, cadeia de auditoria e auditoria específica de componentes.

**Como funciona:** O sistema calcula um score de saúde de 0 a 100 baseado em múltiplas métricas, detecta automaticamente anomalias registrando-as em tabela dedicada, mantém uma cadeia de auditoria com encadeamento hash que impede adulteração, e oferece auditoria específica de mineradores (verificando processamento de tarefas) e de taxas (verificando coerência de cobranças).

**Por que é importante:** Fornece visibilidade contínua, abrangente e verificável sobre o estado da rede, permitindo que qualquer participante audite a saúde e o comportamento de qualquer servidor.

**Novos endpoints:**
- GET /server/audit — Score de saúde completo
- GET /server/audit/anomalies — Lista de anomalias detectadas
- GET /server/audit/chain — Verificação da cadeia de auditoria
- GET /server/audit/miners — Auditoria de mineradores
- GET /server/audit/fees — Auditoria de taxas

**Novas tabelas SQLite:**
- audit_log — Log de auditoria com encadeamento hash
- audit_anomalies — Anomalias detectadas pelo sistema
- db_integrity_log — Log de integridade do banco com encadeamento hash

### 3.4 Console de administrador (NOVO)

O console de administrador é uma funcionalidade completamente nova da Release v5 que permite ao operador do servidor gerenciar todos os aspectos da instância de forma avançada, segura e auditável.

**Características de segurança:**
- Autenticação com senha bcrypt (hash resistente a rainbow tables e força bruta)
- Timeout de sessão de 30 minutos (requer re-autenticação após período de inatividade)
- Registro completo de todas as ações em cadeia de auditoria com encadeamento hash

**Comandos disponíveis (25+ comandos):**
- login/logout — Autenticação e encerramento de sessão

## 4. Mudanças na economia

### 4.1 Supply Cap (NOVO)

**O que é:** Limite máximo absoluto de vouchers que podem existir simultaneamente na rede.

**Valor:** 1.000.000 HPS (constante definida no código-fonte do servidor como SupplyCap).

**Impacto:** Cria escassez artificial programática que sustenta o valor econômico dos vouchers e impede inflação descontrolada. Ao contrário de moedas fiduciárias tradicionais onde bancos centrais podem emitir indefinidamente, ou de criptomoedas com emissão inflacionária contínua, o HPS optou por oferta fixa e conhecida antecipadamente.

### 4.2 Fee Market (NOVO)

**O que é:** Mecanismo de ajuste dinâmico de taxas baseado na oferta e demanda do mercado.

**Como funciona:** As taxas de exchange, upload, registro de DNS e outras operações são ajustadas automaticamente com base no volume de transações, na disponibilidade de vouchers em circulação e no estado geral da economia. Quando a demanda é alta, taxas aumentam; quando há excesso de oferta, taxas diminuem.

**Impacto:** Cria um sistema de preços mais orgânico e responsivo do que taxas fixas, permitindo que a economia se adapte naturalmente a condições de mercado sem intervenção manual do administrador.

### 4.3 PHPS Titles (NOVO)

**O que é:** Instrumentos de investimento que representam porcentagens de participação no mercado de taxas de exchange.

**Como funciona:** Usuários podem comprar títulos PHPS que geram retornos proporcionais ao volume de taxas cobradas nas operações de exchange entre servidores. Preços e disponibilidade são gerenciados dinamicamente pelo servidor.

**Endpoints relacionados:**
- GET /phps/market — Retorna dados do mercado de títulos PHPS
- POST /phps/title/purchase — Compra de título PHPS
- POST /phps/title/redeem — Resgate de título PHPS

**Impacto:** Adiciona profundidade ao modelo econômico, permitindo investimento indireto no funcionamento da economia e renda passiva para participantes de longo prazo.

### 4.4 Voucher Supply Chain (NOVO)

**O que é:** Log de auditoria encadeado por hash para toda mintagem de vouchers.

**Como funciona:** Cada voucher mintado é registrado na cadeia com referência criptográfica (hash SHA-256) ao voucher anterior, criando uma trilha verificável e imutável de toda a emissão monetária desde o primeiro voucher.

**Endpoints relacionados:**
- POST /voucher/supply-chain — Registra entrada na cadeia
- GET /voucher/supply-chain-tip — Retorna ponta atual da cadeia
- GET /supply/audit — Auditoria completa da cadeia

**Impacto:** Permite que qualquer participante verifique que a oferta total não excede o supply cap e que toda mintagem seguiu processo legítimo.

### 4.5 Content Receipt Chain (NOVO)

**O que é:** Log append-only de todos os uploads realizados no servidor.

**Como funciona:** Cada upload gera um registro na cadeia de recebimentos, incluindo hash do conteúdo, identidade do autor, timestamp e contexto. A cadeia é append-only — só cresce, nunca é modificada.

**Endpoint relacionado:** GET /content/{hash}/receipt — Retorna comprovação de recebimento

**Impacto:** Permite verificação de integridade e auditoria histórica completa desde o primeiro conteúdo publicado.

### 4.6 Voucher Locks (NOVO - detalhes na Fase 3 do 2S+1U+1M)

Travas de 60 segundos com confirmação entre servidores para prevenir gasto duplo durante operações de exchange.

### 4.7 Cross-server Voucher Confirmation (NOVO - detalhes na Fase 2 do 2S+1U+1M)

Confirmação de vouchers por pelo menos 1 outro servidor antes de considerar válido para operações significativas.

## 11. Notas importantes

- **Requisitos mínimos de rede:** 2 servidores + 1 usuário + 1 minerador para operação completa do protocolo 2S+1U+1M. Servidores isolados operam em modo degradado com funcionalidade limitada (sem exchange, sem validação cruzada, sem confirmação de vouchers)
- **Migração de banco de dados:** As 7 novas tabelas SQLite requerem migração do banco de dados existente. O servidor deve suportar migração automática ou manual
- **Endpoints de auditoria:** Todos os endpoints de auditoria (/server/audit, /server/integrity, etc.) são publicamente acessíveis, mas retornam dados limitados sem autenticação do cliente
- **Aplicativos Mobile:** Requerem Android 21+ (Lollipop) e .NET MAUI workload instalado no ambiente de desenvolvimento
- **Hash de integridade:** O hash SHA-256 do código-fonte é recalculado a cada compilação. Servidores com código modificado terão hash diferente do esperado
- **Handshake TTL:** Sessões de handshake entre servidores expiram após 5 minutos e precisam ser renovadas continuamente
- **Travas de voucher:** O timeout de trava anti-double-spend é fixo em 60 segundos. Operações que excedam esse prazo precisam de nova trava
- **Score de saúde:** O score de auditoria (0-100) é calculado em tempo real e pode variar entre consultas. Valores abaixo de 50 indicam problemas significativos
- **Compatibilidade retroativa:** O protocolo 2S+1U+1M é opcional para servidores operando isoladamente, mas obrigatório para participação completa na federação
